# 0x03b — Posts: repost, deletion and data links

**Agent-facing.** Part of [[0x03-posts]] (index: module scope, the facade, moderation chain and event bus). The `Post` table these act on: [[0x03a-posts-post]].

**The repost toggle (`POSTS-001`).** `app.posts.service.repost_post`/`unrepost_post`, behind `POST`/`DELETE /posts/{post_id}/repost` (signed in; anonymous is a 401).
- **A plain repost is `is_repost` with no text (null or empty) and no attached media.** A text-less repost with an image (`/compose` allows one) has content of its own, so it is neither toggled, nor deleted, nor counted in `reposted_by_viewer`. Media is read through `app.media.service.processed_media_for_posts` (media/'s public read; attached media is always `Processed`), never media/'s table. Without this rule the `media.post_id` FK would turn the undo into a 500.
- **The target.** Reposting a plain repost reposts its original (looping, since `/compose` rows may already chain plain reposts); a quote repost is reposted as itself. `DELETE` resolves the target the same way, so the toggle is symmetric. An unknown post is a 404 on `POST`, a 204 on `DELETE`.
- **`POST`: one publish path, idempotent, race-free.** Gather actor/target owners and take sorted lifecycle fences before `pg_advisory_xact_lock(hashtextextended('posts.repost:{user}:{target}', 0))` serializes the pair; actor-only locking first would invert reciprocal repost order. An existing plain repost returns 200 (oldest if duplicates exist); otherwise `PublishPostFacade.publish(CreatePostRequest(is_repost=True, original_post_id=target))` returns 201 through moderation/`PostCreated`. Commit/rollback releases locks. No unique index: existing duplicates would require migration review. Hash collisions only serialize unrelated pairs.
- **`DELETE`: the hard delete of a plain repost.** Under the same lock, every plain repost the caller has of the target goes, with the `PostLike`, `Report` and `EventMention` rows that reference it, in one transaction, then 204 (also when there was nothing to remove). It never touches a quote repost, a repost with media, or another user's repost. **409, removing nothing,** when one of those reposts has a reply (re-parenting another user's reply is out of scope) or is itself reposted (the `original_post_id` FK would refuse the delete). `EventMention` is a posts/ table, so the delete reaches into no other module.

**Post deletion (`POSTS-004`, [[wiki/GeneralContext/Decisions/0030-post-deletion-deactivation-and-attachments|ADR 0030]]).**
- **`DELETE /posts/{post_id}`** (`app.posts.service.delete_post`), on `get_current_user`: the author soft-deletes an original, a reply or a quote repost. 204, and 204 again on a repeat, which keeps the first `deleted_at`. 403 for someone else's post (it is public, so 404 would hide nothing), 404 for an unknown id, **409 for a plain repost**: that stays the hard delete `DELETE /posts/{original}/repost`.
- **Nothing cascades.** Likes, reports, mentions, media links, replies and reposts all stay.
- **One visibility rule, `_visible()`**: not deleted, and the author not deactivated. Every read applies it: `query_feed_posts`, `search_posts`, `replies_to` (also behind `GET /posts/{id}/replies`), `reply_counts`, `repost_counts`, `posts_by_ids`, and `visible_post` (`GET /posts/{id}`, so a deactivated author's post is a 404 there too). Recovering an account lifts only the author half, so a post deleted before or during deactivation stays deleted.
- **The repost toggle reads unfiltered on purpose.** `_repost_target`, `_plain_reposts_by` and `unrepost_post` don't apply `_visible()`, so un-reposting a deleted original still works.
- **No new interaction.** Like, unlike, repost and report on a deleted post are 404 (`_undeleted_post`); `PublishPostFacade.publish` refuses a reply or quote whose parent or original is deleted with `PostNotFoundError` (404), before moderation and the insert. An unknown id still reaches the FK, a 400. Reply/repost publication also fences referenced authors, so inactive or deleting/deleted authority blocks publication. Likes/reports fence the actor; their deleted-post check remains separate.
- **Placeholders.** `deleted_post_ids(session, ids)` (one query) is how `feed/` and `notifications/` learn which posts are deleted: a repost of a deleted original gets `reposted_post_deleted` true, and a deleted thread root is `root` null with `root_deleted` true ([[0x06-feed]]).
- **Media limitation, documented and not solved.** A CloudFront URL someone already obtained still works after the post is deleted. Revoking it needs signed URLs or invalidation, a separate design.

**Sports-data attachments (`POSTS-005`, [[wiki/GeneralContext/Decisions/0030-post-deletion-deactivation-and-attachments|ADR 0030]]).** The "game-result attachment" business rule, as one structured link instead of a `#GameId` token. The columns and CHECKs: [[0x03a-posts-post]] "Schema".
- **`POST /posts` takes an optional `data_link`**, a discriminated union on `type`: `{"type": "game_final", "ref_id": <games.id>}`, `{"type": "player_game", "ref_id": <player_game_stats.id>}` or `{"type": "player_career", "ref_id": <players.id>, "scope": "regular" | "playoffs"}`. Each member forbids extra keys and `ref_id` is positive, so a malformed link is Pydantic's own 422 (a `detail` list).
- **`app.posts.data_link.DataLink` is the one mapping** onto the four columns and back (`columns()`, `from_columns()`). `Post.data_link` reads it back, and `PostOut.data_link` is the request's shape, with `scope` null except for a career, or null with no attachment.
- **`PublishPostFacade.publish` refuses before moderation and before anything is written**, after the deleted-parent check. Each refusal is a 422 whose `detail` is a machine code. The post-level rules come first: `data_link_on_reply`, then `data_link_needs_quote_text` (a repost with null or empty text: a plain repost shows its original's attachment). The target comes next, through `events/`' `validate_game_final` / `validate_player_game` / `validate_player_career` ([[0x02-events]]): `link_target_not_found`, `game_not_completed`, `player_did_not_play`, `no_games_in_scope`. A quote repost may carry a link, and a link coexists with an image.
- **No `#GameId` parsing** (the human's decision, with `FRONTEND-013`'s pickers). A `#GameId` token is just text, and a post gets no `EventMention` rows ([[0x03c-posts-likes-mentions]]).
- **Read responses (`POSTS-006`).** `PostView` carries `data_link` and an assembled `data_link_preview`, built from batched `events/` reads ([[0x06-feed]] "Attachment previews"). Preferred-team relevance counts `game_final` and `player_game` links through `linked_game_id` / `linked_line_game_id`, never a career link.
- **The boundary.** Apart from `models.py`'s FK registration, `data_link.py` is the only `posts/` code that reaches `events/`, and only through `app.events.service` and `app.events.errors`. `tests/posts/test_data_link.py` scans `app/posts` and allows `app.events.models` in `models.py` (FK registration) only. `data_link.py` also reads a line's game through `player_game_previews` at create.
