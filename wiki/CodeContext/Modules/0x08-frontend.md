## Look and feel

`src/styles/tokens.css` and `base.css` (`UI-001`) are imported once from
`main.tsx`; `src/styles/tokens.test.ts` recomputes every contrast pair from the
file, unrounded. The rest: CSS Modules plus one global token stylesheet, the system font

eight styling units (`FrontendUI/implementation-plan.md`). This file stays the

### Soft-filled controls and the shared primitives (`UI-010`)

- **Every text-like `input`, `select` and `textarea` is soft filled, from
  `base.css` alone.** No border; the `--color-field` fill; `--radius-lg`
  (12 px); 48 px tall when single-line. No feature CSS changed: every form
  takes the style through the element rule, as before. The fill is under
  3:1 against the page and the card in both themes, so a 1 px
  `--color-border-strong` bottom rule (an inset `box-shadow`) is drawn in
  every state (WCAG 1.4.11, `tokens.test.ts` measures it).
- **Focus moves nothing.** `:focus` only changes the fill to
  `--color-field-focus`; the ring is still the global `:focus-visible`
  outline. No focus rule sets a border, padding or size (`base.test.ts`).
- **Invalid is a ring, not a border.** The controls' `[aria-invalid="true"]`
  adds a 2 px `--color-danger` shadow ring beside the bottom rule. The old
  bare `[aria-invalid] { border-color }` is gone, so a checkbox marked invalid
  gets nothing from it. The field's message (`Field`) is unchanged.
- **Forced colors (`accessibility.md` A20).** Shadows are dropped there, so
  under `@media (forced-colors: active)` the bottom rule is a real border, the
  invalid ring an outline (focus still wins), `SegmentedTabs`' selected tab is
  underlined and `FloatingButton` has a 2 px edge (`styles/forced-colors.test.ts`).
- **No CSS file has `url(` or `@import`**, so styling makes no request; the
  select's chevron is two `linear-gradient`s (`base.test.ts`). The
  placeholder is `--color-text-muted` at full opacity, the colour the
  contrast test measures.
- **`SearchInput`** wraps `Field` and an `input type="search"` with a leading
  `aria-hidden` `SearchIcon`. `SearchBar` uses it: the label, `name="q"`, the
  100 cap and `role="search"` are unchanged. Its text-padding rule is two
  classes deep because `base.css` loads after module CSS in the build.
- **`SegmentedTabs`** is an in-page ARIA `tablist` (automatic activation,
  roving tab stop, ids from `useId`). `Tabs` stays the route tabs.
  **`FloatingButton`** is the 56 px fixed action, a `Link` or a button,
  with a required `aria-label`. Neither has a caller yet: `FRONTEND-018` to
  `-021` adopt them.
- **No runtime styling work** in the three primitives or `FormField`: no
  listeners, observers, `matchMedia`, `requestAnimationFrame` or
  `useLayoutEffect` (`components/ui/ui-css.test.ts`).
- **The bundle has a budget test**, `src/test/bundle-budget.test.ts`. It
  runs Vite's `build()` in vitest and pins the entry JS (149.6 kB gzip,
  471.0 kB raw), the entry CSS (6.25 kB gzip), every other chunk to within
  0.1 kB of its recorded size (and no new one), and no file of 500,000 bytes.
  **A unit that adds or grows a lazy chunk updates its table, in its test
  commit, with the reason.** This thread's later specs carry it forward
  (brief 20, R1).

## Auth (`FRONTEND-002`)

`AuthService` is an interface; `CognitoAuthService` is one implementation of it
and **the only module under `src/` allowed to import the Cognito SDK**. Pages,
hooks and guards depend on the interface, so tests inject a double of it and
never mock the library — a suite that mocked the SDK would pin the mock and keep
passing after the real call signature changed. `src/auth/sdk-isolation.test.ts`
reads the tree from disk and enforces both halves, along with "no module under
`src/auth/` branches on environment". There is one implementation; configuration
differs, code does not, and `App` is the single place that chooses it.

- **`App` is the composition root**: it constructs `CognitoAuthService`, calls
  `installTokenProvider` (which feeds `getIdToken` into `api/client.ts`'s seam,
  re-read on every request so a sign-out lands on the next call), and mounts
  `AuthProvider` *outside* `RouterProvider` — a session does not belong to a
  route.
- **The router is `react-router-dom` 7** (`FRONTEND-016`, 2026-10-20), on
  React 18. Imports keep the `react-router-dom` name, which re-exports
  `react-router` in v7. v7's defaults are v6's `future.v7_*` flags, so none is
  set (`src/test/router-version.test.ts` keeps them out). Not 8: it needs
  React 19 and Node 22.
- **`useAuth().status` has three values**, not two. `"loading"` is distinct from
  `"anonymous"`: collapsing them shows a signed-in user the sign-in page on
  every reload, and the guards render a `role="status"` rather than guess.
- **`GET /users/me` is one shared react-query entry** (`auth/profile.ts`,
  `PROFILE_QUERY_KEY`). Both guards read it, and `ProfileSetupPage` **awaits**
  its invalidation before navigating: `staleTime` is 30s, so the 404 that sent
  the user to the form is otherwise still cached and still believed, and the
  guard bounces them straight back. A guard never requests it without a session.
- **Protected routes are `/compose` and `/notifications`.** `/`, `/search` and
  `/profile/:userId` stay public — the guest feed and profile views are read
  paths ([[0x01-users]]), and a guard on either is a regression. `/create-profile`
  is behind `RequireNewProfile`, which is what stops it being reachable by
  someone who already has a profile.
- **Cognito failures are translated to an `AuthError` carrying the provider's
  error name**, so a page decides which control a failure belongs on without
  importing the SDK to do it. Two are routing states rather than field errors:
  an unconfirmed account goes to `/confirm`, and a throttled resend is an alert
  about no field at all.
- **Tokens are stored by the SDK's default `localStorage`**, accepted for v1.
  The trade-off is real and is recorded rather than hidden: anything that
  achieves script execution in the page can read the ID token. A cookie backend
  is a separate, larger decision and was deliberately not invented here.
- **Nothing logs or renders a token, the pool id or the client id.** The pool and
  client ids are not secrets — they ship in the bundle — but a token is, and
  `src/auth/no-secret-leak.test.tsx` sweeps all five pages for all three.
- **`date_of_birth` is sent by exactly one page** and is never carried off it.
  The field states in its own hint that it is private; the age gate stays on the
  server (a Pydantic 422 naming `date_of_birth`), surfaced on that field in the
  server's own words rather than re-implemented here, because validating in two
  places is how the two rules drift apart.

## Profile and follow (`FRONTEND-003`)

`/profile/:userId` is **one public route with two variants**, chosen by
comparing the id in the path to the signed-in user's. There is no `/settings`
route: settings are a section of a page the user already has an address for, and
a second route would be a second place to decide who is allowed to see it.

- **Date of birth is private, and the component tree is what guarantees it.**
  `OwnProfile` takes `MeOut` (which has the field); `PublicProfile` takes
  `PublicUserOut` (which does not). The one thing they share, `ProfileSummary`,
  takes a username and two numbers — **not a user object** — so it cannot render
  a field it was never handed. Since `UI-008` it also takes one optional
  `action` slot, which `PublicProfile` fills with `FollowButton` so the control
  sits in the header card: a slot for a control, never user data, so the
  guarantee stands. The own profile's date of birth row now says "Only you can
  see this" on screen, not only in a comment. The alternative, one header taking a whole user
  and showing what it finds, is precisely how the backend leaked this field
  before `PublicUserOut` was split off `MeOut` ([[0x01-users]]), and asserting
  "we do not render it" would have left that shape in place.
- **Three cache entries, and they stay three.** The viewed user is
  `["users", <numeric id>]` — a number, because that is what the path parameter
  is in the generated schema, and `["users", "42"]` is a different entry that
  would refetch on every render without ever looking wrong. The follow set is
  `["users", "me", "following"]`. The caller's own profile stays on
  `PROFILE_QUERY_KEY` from `auth/profile.ts` — this page adds no second
  `GET /users/me`.
- **Invalidation names exact keys.** `queryKey` is a *prefix* match, so
  `invalidateQueries({ queryKey: ["users"] })` would refetch every other profile
  the session has looked at as collateral for following one person. Every
  invalidation here passes `exact: true`.
- **Follow is optimistic through react-query's mutation lifecycle.** `onMutate`
  cancels the two in-flight reads (one landing late would overwrite the patch
  with the answer it was already carrying), snapshots both entries and patches
  them; `onError` restores the snapshot and raises a `role="alert"`; `onSettled`
  invalidates, because the server decides the counts and somebody else may have
  followed them meanwhile. **Rollback restores the follower count, not just the
  button** — those are the two things a user sees change. The count lives in the
  viewed profile's cache entry, which is why local state beside it is not an
  option: it drifts out of sync after the second interaction.
- **The follow set is read by `ProfilePage`, not by the button.** The button is
  the last thing on the page to mount, so owning the query would start it only
  once the profile had arrived, and the button would spend that round trip
  telling someone who already follows them to "Follow".
- **An anonymous visitor sees the control and is sent to sign-in by it**,
  carrying `state.from` the way `routes/guards.tsx` does. No authenticated read
  is issued at all without a session — not the profile, not the follow set, not
  the write — because a 401 here is a failure the page would then have to
  explain away on a route that is deliberately public.
- **`PATCH /users/me` carries only the fields that changed.** The backend reads
  the body with `model_fields_set` semantics ([[0x01-users]]): a field *absent*
  is left untouched, while a field present as `null` clears it. Sending every
  control on every save would therefore wipe whatever the user did not touch.
  Emptying the description is the one case `null` is correct for — that is the
  user asking for it to be cleared. `username` and `date_of_birth` are not on
  `UpdateMeRequest` and are not editable here.
- **This unit ships without a profile-picture control.** The upload widget
  belongs to `FRONTEND-004`, which has not landed; a second uploader here would
  be a duplicate media path ([[0x00-architecture]] Connection rule) and would
  need deleting rather than merging. `profile_picture_media_id` is never sent.
- **`AppLayout` links "Your profile" by id**, because the route has no fixed
  address for "me". It renders only for a visitor who has a profile, and reads
  it through the same shared query gated on the same session the guards use —
  so the shell asks the API nothing until somebody signs in, and never links to
  `/profile/undefined`.

## Contracts the foundation pins

Changed only with the tests that pin them, because six later units build on
each:

- **Routes**: `/`, `/compose`, `/notifications`, `/search`, `/profile/:userId`,
  `/sign-in`, `/sign-up`, `/confirm`, `/forgot-password`, and `*`, plus
  `/create-profile` from `FRONTEND-002`. The catch-all is the app's own
  not-found view — deliberately, so react-router's built-in error element can
  never stand in for a view the app does not have and make a missing route read
  as green. `routes.test.tsx` sweeps every route asserting no *other* view's
  heading is on screen, so the headings are pinned and anchored; since
  `FRONTEND-002` the sweep also records which of the three guard states makes
  each route the one that renders.
- **Client surface**: `createApiClient(provider)` (the factory a test double is
  injected through), the `apiClient` singleton the app uses, and
  `setTokenProvider(provider)`. The singleton reads the *current* provider
  through a closure, so `FRONTEND-002` can install the real Cognito one after
  module load.
- **No `Authorization` header at all** when the provider returns null — not an
  empty one. `Bearer null` and `Bearer ` both make the backend verifier 401 an
  anonymous request, which breaks the guest feed for a reason nobody would look
  for.
- **`config.ts` exports one `config` object**, throws at module load, and names
  *every* missing variable rather than the first.
- **The base URL is resolved against `window.location.origin`.** `/api` handed
  straight to `createClient` throws `Invalid URL` from Node's `Request`
  constructor under vitest, before msw sees it. Same origin either way — this
  changes nothing about the deployed contract and adds no CORS.

## Build facts the frontend depends on

None lives in `frontend/`. The first two were wrong until `FRONTEND-001` needed
them:

- **CI enforces the contract.** The `openapi-drift` job in
  `.github/workflows/test-agent.yml` regenerates `backend/openapi.json`, then
  regenerates `src/api/schema.d.ts` from that fresh export, and fails if either
  committed file differs. It runs on any backend or frontend change and is part
  of the required `gate` check. A unit that changes a route must commit both
  regenerated files.

- **`backend/openapi.json` is pinned to LF** in `.gitattributes`. It is compared
  byte-for-byte against a fresh export, and `core.autocrlf=true` on Windows
  checked it out as CRLF — 2429 carriage returns, the drift gate red on a clean
  clone where nothing was wrong.
- **`docker/backend.Dockerfile`'s `test` stage copies `scripts/` and the
  committed schema.** Without them that suite passes locally and fails in CI,
  reporting a missing file rather than the missing `COPY`. The `jso[n]` glob is
  deliberate — see the comment there.

## Test harness facts

These exist so a test can use an ordinary static `import` of the thing it tests,
and an ordinary `FormData` to upload a file. Each was found by a test that passed
locally and could not pass in `frontend-test`, which is the same shape as the two
build facts above. `src/test/harness.test.ts` pins them, so none is a rule
anybody has to remember:

- **`vite.config.ts`'s `test.env` supplies all five `VITE_*` values.**
  `config.ts` throws at module load on a missing one, and `.dockerignore`
  excludes `**/.env.*` — so the container and CI have no env file, while a
  developer's machine has `.env.local` and hides the failure. `test.env` also
  outranks `.env.local` (`.env.[mode]` beats `.env.local`), so a test run reads
  the same fake pool id everywhere and the real dev pool is never reachable
  from a test.
- **`setupTests.ts` calls `server.listen()` at module scope, not in
  `beforeAll`.** `openapi-fetch`'s `createClient` captures `globalThis.fetch`
  when it is constructed, and `api/client.ts` constructs `apiClient` at module
  load. A setup file's `beforeAll` runs *after* the test file's whole import
  graph, so listening from a hook left every statically imported `apiClient`
  holding the unpatched fetch: its requests left for the real network and
  failed as `ECONNREFUSED`, with nothing pointing at msw.
- **`setupTests.ts` gives jsdom's `Blob` the readers it does not implement** —
  `arrayBuffer()`, `text()` and `stream()`, built on the `FileReader` jsdom does
  provide, and installed only when absent so a future jsdom wins over the patch.
  jsdom stops at `slice`, `size` and `type`, and every path that serializes a
  body containing a file reaches for one of the three — so without them a
  `FormData` carrying a `File` cannot be sent from a test and a handler cannot
  read one back. **It has to live in the setup file**: the body is serialized by
  the runtime, long after any per-test setup, so no fixture can reach it, which
  is why `FRONTEND-004` could not fix it from inside its own permitted paths.
  The failure this removes was the nastiest of the three. On a developer's Node
  22 it survives; on the Node 20 in `docker/frontend.Dockerfile` and CI it throws
  `AssertionError [ERR_ASSERTION]: false == true` from inside msw's handler
  lookup, so the test fails as an empty recording, points nowhere near the cause,
  and does so only in the container. Neither the multipart encoding nor Node 20
  is at fault — that same body parses under both versions with plain undici; it
  is the jsdom interaction.
  The workaround it existed to remove is gone: `MediaWidget` builds an ordinary
  `FormData` and `src/test/compose.ts` reads it back with `request.formData()`.
  An upload is written the plain way here.
- **`src/test/form-data-file-names.ts` keeps a file's name across Vitest 4's
  jsdom/Node bridge** (2026-10-06, the Vitest 3 → 4 upgrade that cleared the
  critical `tinypool` advisory). Under Vitest 4, `FormData`, `File` and `Blob`
  are jsdom's while `Request` and `fetch` are Node's, and Vitest converts a
  jsdom `FormData` into a Node one by appending each file as a bare `Blob`, so
  every upload reached msw named `blob`. The module wraps the global `Request`
  and does the conversion itself, names included; `setupTests.ts` imports it
  **before** msw, which builds its `Request` from the global. It reads the
  bytes the way Vitest's own bridge does (jsdom's `impl` buffer), because a
  request body is built synchronously. `harness.test.ts` and
  `MediaWidget.test.tsx` are what caught it, and they pin it. Vitest 5 has the
  same bridge, so this stays until upstream keeps file names.
- **`tsconfig.app.json` lists `vite/client` and `node` in `types` explicitly.**
  Vitest 3's `vitest/globals` pulled both in transitively and Vitest 4's does
  not, so the disk-reading tests (`node:fs`, `process.cwd()`) and CSS/SVG
  imports stopped type-checking.

## Settled contracts

These are decided and are not re-litigated by a unit that finds them
inconvenient:

- **API base URL** is `VITE_API_BASE_URL` = `/api`, same origin in both
  environments. Vite's `server.proxy` strips `/api` in dev; a CloudFront Function
  strips it in production ([[0x00-architecture]] "Frontend ↔ API contract").
  There is no CORS anywhere and none is to be added.
- **Types are generated**, never hand-written: `openapi-typescript` produces
  `src/api/schema.d.ts` from `backend/openapi.json`, and `openapi-fetch` is the
  only HTTP client.
- **Auth is real Cognito** — a hand-made dev pool locally, `Fanwire-Auth`'s pool
  in production. Never an emulator or an in-house fake. The SPA sends the
  **ID token** as `Authorization: Bearer`; the backend rejects access tokens
  ([[0x01-users]]).
- **A 404 from `GET /users/me`** means "authenticated, no profile yet" and routes
  to profile creation. It is a state, not an error.
- **Date of birth is private**: the user's own profile and settings only, never a
  public profile view.
- **Configuration is read in exactly one module** (`src/config.ts`), which
  validates at load and throws on a missing value. Vite inlines `VITE_*` at build
  time, so the production bundle is only correct for the environment it was built
  against: the production Cognito ids don't exist until `Fanwire-Auth` deploys
  ([[wiki/CodeContext/Standards/build-deployment|Build & Deployment]] → "Rebuilding the SPA").

## Compose (`FRONTEND-004`)

`src/features/compose/`, at `/compose` behind `RequireAuth`; since `FRONTEND-020`
an overlay over the current page (below, "The compose modal"). The page owns
one `ComposeMediator` and hands it to all three controls; that is the whole of
the wiring between them.

**The four patterns are assigned by [[wiki/CodeContext/Standards/gof-patterns|GoF patterns]], not chosen here**, and
each owns one piece:

| Piece | Pattern |
|---|---|
| Assembling `CreatePostRequest` across steps | `PostBuilder`, validation in `build()` |
| Text box ↔ attachment picker ↔ media widget | `ComposeMediator` |
| Undo after a sports-data link is attached or replaced | `DraftSnapshot` (Memento) |
| Quick-post templates | `PostTemplate.clone()` (Prototype) |

- **The mediator's isolation is enforced from disk**, by
  `component-isolation.test.ts`, which reads the three component sources and
  checks the import specifiers in all six ordered pairs. A behavioural test
  cannot see this: a media widget that imports the text box directly and pokes at
  it still renders and still passes every rendering test. Same shape, and the
  same reason, as `auth/sdk-isolation.test.ts` and `test/env-usage.test.ts`.
- **`getDraft()` returns the same object until something changes the draft.** It
  is the `useSyncExternalStore` snapshot, which React compares by identity, so a
  fresh object per call is an infinite render loop rather than a failing
  assertion. Every mutation publishes a *new* draft object and nothing edits the
  published one in place.
- **A quick-post template is cloned, never handed out.** `clone()` copies the
  media-id array too: a shallow copy passes every obvious test and fails on the
  *second* use of the same template.
- **File bytes go straight to the bucket and never through `apiClient`.** Two
  reasons, both hard: routing them through FastAPI would put a Lambda body-size
  limit in front of every image, and `apiClient` attaches the Cognito **ID
  token** — sending that to S3 would leak it to a service that has no use for it.
  So `POST /media/uploads` (the ticket) goes through `apiClient` and carries the
  token; the multipart POST to `upload_url` is a plain `fetch` with no
  `Authorization` header at all.
- **The presigned fields go first, in the order the API returned them, and
  `file` goes last** — S3 ignores everything after the file part. It is an
  ordinary `FormData`, which serializes in insertion order, so appending in that
  order is the whole of it and `fetch` derives the `Content-Type` and its
  boundary; setting that header by hand would override the boundary the body was
  written with. The ordering is not left to a comment — `MediaWidget.test.tsx`
  asserts the field order that actually reaches the bucket.
- **The real status values are `uploaded`, `scanning`, `processed` and
  `rejected`** — lower-case, four of them, from `MediaStatus` in the generated
  schema. **There is no `Quarantined` value**: where prose says quarantined it
  means *not yet `processed`*, and both `uploaded` and `scanning` are
  un-attachable. `rejected` is a refusal (`FRONTEND-020`: the image is
  removed and one red line says so). The widget polls `GET /media/{media_id}`
  once a second on its own timer, from the upload's end, and stops at a
  terminal status or at the 30 s bound (below).
- **Locally there is no GuardDuty, so an upload against the real dev buckets
  stays un-`processed` forever.** That is correct behaviour, not a hang: nothing
  moves the row past `uploaded`. Since `FRONTEND-020` the 30 s bound refuses it
  with the red line, which is what local dev shows. The dev-only script that would run the processing pipeline on
  demand is `MEDIA-002` and does not exist yet ([[0x04-media]]).
- **No `URL.createObjectURL` anywhere.** jsdom does not implement it and
  `setupTests.ts` is not this unit's to change — and the served thumbnail is the
  honest thing to show anyway, since it is what everyone else sees once the post
  is published, EXIF-stripped and resized by the pipeline rather than the
  original off the user's disk. The widget shows the file's **name** while the
  upload is pending and an `<img>` at `config.mediaBaseUrl` + `s3_key_thumbnail`
  once it is `processed`.
- **The file input carries no `accept` attribute.** The browser's own filter
  drops a file the user chose without telling them why, and the type rule —
  jpeg, png and webp, SVG excluded by name ([[0x04-media]] Security
  requirements) — is one the user has to be able to read. The client-side type
  and size checks are for that message only; S3's policy and the processing
  Lambda's Pillow parse are the real gates and run regardless. `max_bytes` exists
  only in the ticket response, so the size check necessarily comes *after*
  `POST /media/uploads` and necessarily before the bucket POST.
- **The `#`/`$` mention dropdown is gone (`FRONTEND-013`, the human, 2026-10-22).**
  `POSTS-006` stops parsing `#GameId` in new posts, so a token inserted by a
  dropdown would silently do nothing, and `$TEAM` never resolved to anything. A
  typed `#GameId123` is sent as plain text. Old posts' resolved mentions still
  render as links in the feed (`PostText`, unchanged). `MentionAutocomplete`,
  `mentions.ts`, the `mention-inserted` event and Undo mention are deleted.
- **The address is how another feature opens the composer in a context.**
  `/compose?reply_to=<id>` and `/compose?repost_of=<id>` are read by
  `ComposePage` and handed to the `ComposeMediator` it builds; the mediator has
  taken those two ids since this unit, but nothing outside the page could reach
  them, so "reply to post 42" had no expression at all. A route is the one seam
  a feature folder can offer another without being imported by it
  ([[0x00-architecture]] Connection rule) — which is what lets `features/feed/`
  own a reply control while reimplementing no part of composing, from a unit
  that has `features/compose/**` in its `forbidden_paths`. **A parameter that is
  not a positive integer is no context rather than a broken one**: the address
  bar is user input, and `Number("x")` is `NaN`, which JSON sends as
  `parent_post_id: null` on a post still claiming `is_reply: true`. The context
  is asserted through the `POST /posts` body, because reply context is not
  content — `canBuild()` says so — and the composer renders nothing for it.
- **Nothing is fetched when the page mounts.** The pickers fetch when they open,
  a pre-filled link when the address names one, templates are stored in the app, and the media poll
  starts at the first upload. `routes.test.tsx` renders `/compose` under
  `onUnhandledRequest: "error"`, so a query on mount would break a file this unit
  is not allowed to touch.
- **A failed `POST /posts` preserves the draft** — the text, the attachment, a
  message saying what happened, and a retry that sends the same request. Losing a
  user's typed text on a 500 is the worst thing this page can do and the failure
  most likely to survive review, because the happy path is what gets clicked. The
  composer is cleared in exactly one place, `onSuccess`, and clearing it clears
  the media widget's own card as well: the draft alone cannot say a reset
  happened, since an emptied draft and a never-filled one are the same value, so
  the widget watches a reset counter on the mediator. A stale thumbnail over an
  empty composer is the failure that guards against.
- **The media widget's field error is the `InlineAlert` itself, named by id.**
  The file input's `aria-describedby` points at `compose-media-error`, which is
  `InlineAlert`'s `id` prop on the `<p role="alert">` (2026-10-07,
  `FrontendUI/decisions.md`). `UI-006` first put the id on a wrapper `<div>`,
  because `components/ui` was outside its paths; the prop replaced it. The
  description is the message alone, because the alert's icon is `aria-hidden`;
  `compose-style.test.tsx` pins both that and that the target is the alert.
- **The stats picker opens over compose** (`FRONTEND-021`, below). Its dialog
  sits outside the compose form so Enter cannot publish the draft. The three
  mediator colleagues remain isolated by `component-isolation.test.ts`.

### The compose modal (`FRONTEND-020`)

Brief 20, stage 2. You can post from anywhere: a floating **+** opens compose
over the page you are on.

- **`/compose` is an overlay route** (`routes/ComposeModal.tsx`), rendered by
  `BackgroundRoutes` over the page it was opened from, which stays mounted
  (the same recipe as the thread modal). It uses UI-010's `Dialog`, titled
  "Compose". The composer is its own lazy chunk, waited for inside the
  dialog and never behind the page's Suspense.
- **The history state is read only in `modal-flow.tsx`.**
  - A compose entry carries `{ background?, composeOpenedInApp: true }`.
  - `useComposeLinkState()` builds it. On a page, `background` is that page.
    Inside the detail modal, it is the flow's background, so the detail
    closes under compose and only one dialog is ever open.
  - `useComposeClose()` is the one way out, for Close, Escape, the backdrop
    and a published post. It steps one entry back when the entry was opened
    in the app, which returns you to the page, or to the detail, whose own
    entry still carries its flow. A direct load or a reload has no flag, so
    it replaces the entry with `/`.
  - The "Post about this" links on the game page, box-score rows and the
    player page carry this state. Their addresses are unchanged.
- **The guard's rules are `RequireAuth`'s.** `ComposeModal` reads the
  account status the shell already holds (`ShellAccountStatus`, provided by
  `AppLayout`), so opening compose asks the API nothing.
  - A guest is redirected to `/sign-in` with `from`, and a profile-less
    account to `/create-profile`, before any dialog renders.
  - Loading, deactivated and unavailable states render `RequireAuth` inside
    the dialog.
  - While the account or the chunk is still loading, the dialog waits up to
    500 ms before showing a loading line. A guest's redirect therefore
    never flashes a dialog first, and a quick chunk opens straight on the
    composer.
- **The + replaces the Compose nav item.** It is `FloatingButton` in its
  `onClick` form, since its link form takes no state, named "Compose a
  post", and shown only to an active account. `main` is padded at the bottom
  so the last card's controls scroll clear of it: 8.5rem on phones and 5rem
  from 40em (`floating-clearance.test.ts`).
- **A published post closes the modal**, the same way Close does, and
  invalidates the `["feed"]` prefix. Compose spells the key and doesn't
  import the feed feature. A failed post keeps the draft and the modal.
- **The attach row** sits under the text box. Both buttons are icon-only and
  at least 44 px:
  - the paperclip, "Attach an image", opens a visually hidden file input
    with no `accept`;
  - the bar chart, "Attach stats", opens the stats picker dialog
    (`aria-haspopup="dialog"`, since `FRONTEND-021`).
  An attached link's summary shows whether the picker is open or not.
- **The image check** (`MediaWidget`, shared with the thread's reply box):
  - **The tile:** from the choice onward, a fixed-size tile shows the file
    name under a static overlay. It has no animation (A8) and a `role=status`
    line, "Checking the image…".
  - **Auto-attach:** on `processed` the thumbnail replaces the tile and the
    image is attached, with no second press, plus a "Remove image" control.
  - **Polling:** the poll runs once a second on the widget's own timer,
    starting when **the bucket upload finishes** (the human, 2026-10-24: a

    `rejected`, or nothing by the bound removes the tile and shows one red
    line with a ✕: "The image you attached is too large or cannot be
    accepted".
  - **Other failures:** a failure to reach the API or the bucket keeps "We
    could not upload that image. Please try again.".
  - **Post and Reply** are disabled while an image is being checked
    (`ComposeMediator.isMediaChecking`).
- **Bundle:** the overlay, the + and the new widget add about 0.66 kB gzip
  to the entry, against an allowance of 1 kB
  (`src/test/bundle-budgets/FRONTEND-020.ts`).

## Notifications (`FRONTEND-006`)

`src/features/notifications/`, wired at `/notifications` behind `RequireAuth`.
The page owns the list and the clear mutation; the row owns its actor; the
preference is its own component. Clearing is a soft delete on the backend
([[0x05-notifications]]) and **nothing here exposes that** — from the UI it is a
204 and the entry is gone.

- **The list and the preference are sibling cache keys**, `["notifications",
  "list"]` and `["notifications", "preference"]` — *not* the preference nested
  under a list at `["notifications"]`. `queryKey` is a prefix match, so the
  nested spelling makes every clear cancel and refetch the preference, and is
  correct only for as long as nobody forgets `exact: true`. Two disjoint keys
  make that wrong turn unavailable rather than merely discouraged. Every
  invalidation still passes `exact: true`, the way `FRONTEND-003`'s follow
  control does.
- **The actor is read under `["users", <numeric id>]` — deliberately the same
  entry `features/profile` reads a viewed user from**, so opening a profile from
  a notification finds it warm. The key is *redeclared* rather than imported: a
  feature folder never reaches into another feature's internals, and a
  two-element array is a smaller cost than that coupling. The id is a number,
  because that is what the path parameter is in the generated schema.
- **The actor is a query per row, and that is what makes it one request per
  actor.** react-query deduplicates by key while requests are in flight and
  serves the rest from the entry, so ten rows from one actor issue one
  `GET /users/{user_id}`. A `useEffect` fetch per row renders exactly the same
  thing and issues ten — which is why the test counts requests rather than
  asserting on what is rendered.
- **The clear mutation lives on the page, not the row, and its rollback is a
  snapshot.** The row unmounts the instant the optimistic patch lands, so a
  mutation owned by it would take its own `onError` and its failure message down
  with it, and the entry would reappear with nothing saying why. `onError`
  writes the snapshot array back *verbatim*: restoring as `[...remaining,
  cleared]` puts the entry at the end, which is also what a naive
  refetch-on-error produces, and an entry that reappears somewhere else reads as
  a second bug rather than as a failure that was undone. The tests clear the
  **middle** of three rows for exactly this reason — clearing the last one cannot
  tell the two rollbacks apart.
- **Where an entry points is decided by its `type`, never by `reference_id`
  alone.** On a `follow`, `reference_id` *is* the actor's user id
  ([[0x05-notifications]]), so a row that sent every `reference_id` to `/posts/`
  would link to a post whose id is really a user's and look entirely plausible.
  `reference_id` is nullable, so a reply or repost without one reads the same
  with plain text where the link would be.
- **`/posts/:postId` does not exist yet.** A reply or repost links to
  `/posts/{reference_id}`, which currently lands on the app's own not-found
  view. That is accepted, not overlooked: the address mirrors the API's own
  `/posts/{post_id}` and the `/profile/:userId` convention, and adding a route
  would have meant editing the pinned sweep in `routes.test.tsx` for a page no
  unit owns. **Whoever builds a post or thread page should serve that address**
  rather than invent a second one.
- **An unrecognised `type` renders a generic entry.** The switch could be written
  exhaustively — `NotificationType` is the closed set `follow | reply | repost`
  and the compiler would agree — but the bundle outlives the contract it was
  built against. A list that throws on one row takes down the rows it *does*
  understand, and one that renders nothing is indistinguishable from a broken
  fetch.
- **The email toggle is a native checkbox and is never disabled.** Email is a
  deliberate no-op in every environment today (`SesEmailSender` skips while
  `NOTIFICATION_FROM_ADDRESS` is unset, and no SES identity is verified —
  [[0x05-notifications]]), but that is a **deployment state, not a feature
  flag**: the toggle stores a real preference, and a control that apologised for
  the environment it happens to run in would have to be found and removed the day
  SES is verified. Native over `role="switch"`: focusable, space-operable and
  readable by assistive technology with no code. Request failures are a
  `role="alert"` beside the field rather than `Field`'s own message slot, which
  is the split `FormField` documents.
- **The page re-decides nothing about who may see it.** `RequireAuth` in the
  route table is the one place that answers that; a second check here would be a
  second answer free to disagree with the first, and its "not signed in" branch
  would be unreachable. `ProfilePage` gates because *its* route is public — this
  one is not.
- **The preference card is there from the first render** (`UI-007`):
  `EmailPreference` renders its loading and failure lines inside the same
  one-row `Card` as the checkbox, so the list below doesn't jump when the read
  lands. To put the checkbox before its label, the page's module CSS turns
  `Field`'s root into a row from inside `.preference` (`.preference > div`).
  That reaches into `Field`'s markup, which `Field` otherwise owns; it is
  scoped to this one card, and a `Field` that grows a checkbox layout of its
  own should replace it.

## Feed and threads (`FRONTEND-005`)

`src/features/feed/`, wired at `/` and **public** — the guest feed is a read path
by decision ([[0x06-feed]] Security), and a guard on `/` is a regression.

- **`PinnedPostDecorator` is deliberately not built, and this is the record of
  why.** [[wiki/CodeContext/Standards/gof-patterns|GoF patterns]] names it
  alongside `LiveScoreTickerDecorator` (itself removed by `EVENTS-003`, below),
  so the next reader of that document will reasonably ask where it went. **No backend field marks a post as pinned** —
  [[0x03-posts]] has no such column — so it would decorate a condition that
  cannot occur. YAGNI, and the acceptance criterion is written as an absence
  precisely so a test can pin it: `feed-isolation.test.ts` sweeps the whole of
  `src/` for the name, and assembles that name from fragments so the sweep does
  not match the file performing it. **Do not re-add it** without a column that
  makes it mean something.
- **One request, and the UI never learns which ranking it got.** A guest and a
  signed-in visitor both issue the same `GET /feed`; the backend picks between
  `GuestRecentStrategy` and `FollowsAndPreferredTeamStrategy` ([[0x06-feed]]).
  An `if (isSignedIn) renderPersonalized()` duplicates a decision the backend
  already made and drifts the moment the ranking changes. This is pinned twice,
  because neither half is sufficient: behaviourally, the same response is
  rendered to both visitors and compared whole; and structurally, from disk,
  because a branch that happens to agree for a fixture passes every behavioural
  assertion. The structural half bans the *vocabulary* of that decision from the
  unit's code, with comments stripped first — a good implementation should stay
  free to explain that the backend chose. It is a lexical proxy for the
  property, not the property: a branch spelled `if (session)` is caught only by
  the behavioural half.
- **Paging is an explicit "Load more" control, not a scroll sentinel**, and that
  is a harness constraint rather than a UX preference. **jsdom implements no
  `IntersectionObserver`**, and `src/setupTests.ts` — the only place a polyfill
  could live — is outside this unit's `allowed_paths`, so a scroll-triggered
  implementation would have been untestable from inside the unit. Acceptance
  criterion 1 asks that the next page be loaded *using `next_before_id`* and that
  it stop when the response reports none; both are properties of the request, not
  of the gesture. Same shape as the `URL.createObjectURL` decision above, and the
  second time this class of thing has decided a unit's design.
- **`getNextPageParam` returns `next_before_id` straight through.** react-query
  already reads `null` as "no further page", so "stopping cleanly" needed no code
  of its own — and the cursor is the one the *response* carried, never the last
  id on screen. Those agree until view assembly silently drops a post whose
  author was soft-deleted, which [[0x06-feed]] says it does.
- **Feed pages are not keyed by cursor.** `["feed", "pages"]` is the whole
  infinite query; `["feed", "thread", <postId>]` is one thread, as the modal
  reads it (a 404 is cached as `null`, `FRONTEND-010`). A key
  carrying `before_id` would make page two an entry that page one could never
  extend.
- **The optimistic like's snapshot is not in the button.** A post is not owned by
  one cache entry: it is in whichever feed page it arrived on, in every open
  thread that shows it, in search results, and since `UI-009` inside
  every repost of it (`reposted_post`), so state beside the cache moves one
  copy and leaves another stale **on the same screen**. `onMutate` patches every
  entry under `["feed"]` that actually holds the post, and that filtered list of
  entries *is* the rollback context — which is how `onSettled` can still
  invalidate **exact** keys, computed from the patch rather than assumed. The
  count moves with the control, and both are restored on failure; those are the
  two things a user sees change.
- **Every post renders through one `PostNode`, including at depth.** A thread is
  replies, and replies are posts ([[wiki/CodeContext/Standards/gof-patterns|GoF patterns]] Composite). The card
  renders from its `post` **prop** and the thread query supplies only the
  replies — a node that preferred the thread response's own `root` would render
  a post from a different cache entry than its parent is rendering from.
  **Since `FRONTEND-010` there is no inline thread**: no `Show replies`
  disclosure and no `nested` prop. Replies are read only by the thread modal
  (below), where each is again a `PostNode` card.
- **`GET /feed/thread/{id}` is one level per request.** It returns the root
  plus **direct** replies only; a deeper level is the same request on the
  reply, which the modal makes when a reply's own thread is opened. The
  endpoint does not offer a whole thread and the shape exists to stop a client
  trying.
- **A media item that cannot be shown keeps its frame** (since `FRONTEND-015`,
  which replaced "leaves nothing behind": a dropped picture is a layout
  shift). An error, a `null` `s3_key_public` or the card's timeout renders no
  `<img>`, and the frame holds a neutral "Image unavailable" line instead.
  Media renders from `s3_key_public` (the served image), not
  `s3_key_thumbnail` — the composer's widget uses the thumbnail, and these are
  different jobs.

### The post card (`UI-009`)

- **One control shape, `PostAction`.** Like, reply and repost are each an
  icon-only ghost `sm` control (the hit area stays above 24 × 24) followed by
  its count as text: "0 likes", "1 like", "1,000 replies". `countText`
  (`counts.ts`) formats the number with `Intl.NumberFormat` and picks the
  noun by hand, singular at exactly one. The count is outside the control and
  never in its name, so a stranger's like does not rename the button.
- **Fixed names, `aria-pressed` for state (the human, 2026-10-16).** The
  buttons are always "Like" and "Repost" (the `aria-label`); the viewer's
  state is `aria-pressed`, and a pressed control swaps to `HeartFilledIcon`
  or the heavier `Repeat2FilledIcon`, so the state is not colour alone.
  Reply is a link named "Reply", with no pressed state. This supersedes the
  task's "Unlike"/"Undo repost" wording and `components.md` §2's "not
  `aria-pressed`" for these two controls: a name that changes *and* a pressed
  state is the same fact said twice. `LikeButton` is gone, folded into
  `PostAction.tsx`.
- **One optimistic pattern, `TogglePostAction`.** Like and repost differ only
  in the request (`setLiked`, `setReposted`) and the edit (`withLike`,
  `withRepost`); the cancel, the snapshot of every entry that holds the post,
  the patch, the rollback with an `InlineAlert`, the exact-key invalidation
  and the sign-in redirect for a guest are written once. The control is
  disabled while its request is in flight. `cacheHolds` and `mapCachedPosts`
  also look inside a post's `reposted_post`, so liking an original through a
  repost card moves the original's own card in the same render.
- **Reply does not move the reply count.** The count changes when the post is
  read again after a reply exists (the thread modal invalidates every cached
  copy of the parent once its reply is posted).
- **A plain repost is the original.** Plain means `is_repost` with no text
  and no media, the same rule as [[0x03-posts]] "The repost toggle". It
  renders as a line "↻ <name> reposted" (the name links to the reposter's
  profile), then the original's content, controls and counts, all acting
  on `reposted_post.id`, and opening the original's thread. A null `reposted_post` reads "This post is
  unavailable". Still one `PostNode`: the node picks its subject, the post or
  its original, and renders that.
- **A quote repost is its own post** with the original inside as a compact
  bordered box (author, time, text clamped to three lines, no controls).
  Its time links to `/posts/<original id>` and a click inside the box opens
  the original's thread (`FRONTEND-010`); the author still links to their
  profile. A null original there reads "This post is unavailable".
  **A plain repost of a quote shows no box**: `reposted_post` is one level
  deep ([[0x06-feed]]), so the quote inside always arrives with its own
  `reposted_post` null, which is the depth cut, not a missing original.

### The thread modal (`FRONTEND-010`)

`src/features/thread/ThreadModal.tsx` at `/posts/:postId`, over whatever page
the reader was on. Public: a thread is a read path; replying needs a session.

- **The background-location pattern, without a re-mount.** Every link into a
  thread carries the page it left as `background` (now inside the flow state,
  below). `routes.tsx` keeps the
  table as data in two lists, `pages` and `overlays`, under one pathless
  `AppLayout` route whose only child is a splat rendering
  `BackgroundRoutes`. That component always renders the pages with
  `useRoutes(pages, location)` at **one tree position**, against the real
  location, or the background while an overlay matches (the feed, `/`, for a
  direct load), then the overlay after it. Only the location passed changes,
  so the page underneath keeps its instance, DOM, local state, data and
  scroll; tests pin node identity, an uncontrolled input's text, and no second
  read. Switching between `<Outlet />` and something else at the page's
  position is the re-mount this avoids. The layout route has to be pathless:
  with `path: "/"` it matched `/` alone and outranked the splat.
- **Opening.** The timestamp is a link to `/posts/<subject id>` (the
  keyboard and screen-reader path); a click elsewhere on the card is a mouse
  convenience that ignores clicks on or inside `a, button, input, textarea,
  select, label`, clicks that end a text selection, and a click on the thread
  already open (it would push a duplicate entry). The card has no `tabindex`
  and no wrapping link. Reply goes to `/posts/<id>?reply=1`, and the reply
  count is a link to the thread too. A link from inside the modal carries the
  **original** background, so the page underneath never becomes a thread.
- **One flow, not a stack (`FRONTEND-011`).** A detail's history entry
  carries `{ background?, depth }`, read and written only by
  `src/routes/modal-flow.tsx`: `useDetailLinkState()` (a link on a page
  starts a flow at depth 1 with this page as background; a link inside
  `ModalFlowScope`, which `BackgroundRoutes` wraps every overlay in,
  continues it at depth + 1 with the same background), `useFlowBackground()`
  (the page to keep underneath) and `useModalFlow()` (`{ depth, back, close
  }`). No other file reads `location.state`; `src/routes/modal-flow.test.tsx`
  scans for it. Game and player details joined it in `FRONTEND-014` (below)
  without a change to that shape; the module gained two read-only hooks.
- **Closing leaves the whole flow.** Close, Escape and a backdrop click go
  back `depth` entries with a background, which is the origin's own entry:
  its address, query string, loaded pages and scroll are as the reader left
  them. With no background (a direct load or reload) they go back `depth -
  1` entries and replace the first one with `/`, so nothing of the flow is
  left behind home and an earlier, unrelated history entry is never
  reached. A second press before the step lands is ignored.
- **Back steps one detail.** `Dialog`'s optional `onBack` shows a 44 px
  "Back" icon button before the title when `depth > 1` (`navigate(-1)`); the
  browser's Back does the same and, from the first detail, returns to the
  origin. The one `Dialog` stays mounted across details, so focus returns to
  the first opener when the flow closes.
- **Known gap:** opening a nested thread from a reply's timestamp removes the
  focused link, and focus falls to `body` with the modal still open (Tab
  re-enters the dialog). Moving focus to the dialog's heading on a detail
  change is still a follow-up: `FRONTEND-014` did not take it, and a
  preview or box-score link inside the modal has the same gap.
- **`components/ui/Dialog`**: a native `<dialog>` opened with `showModal()`
  (top layer, inert page, focus kept inside), the title as its heading and
  accessible name, a Close button, the prevented `cancel` event as Escape,
  and focus returned to the opener. **A backdrop click is a click whose
  target, and whose mousedown's target, is the `<dialog>` itself**: the
  dialog has no padding and does not scroll (its content does), so neither a
  click on the scrollbar nor a selection dragged out onto the backdrop closes
  it. jsdom has no `showModal`/`close`; `setupTests.ts` shims them on
  `HTMLDialogElement.prototype`, only when absent. The backdrop uses the
  `--neutral-950` primitive at 0.6 opacity: there is no scrim token.
- **Content.** The root `PostNode`, then the composer, then the direct
  replies oldest first (the API's order), each a `PostNode`. "Post not
  found" for a 404 or a non-numeric id (no request); an `InlineAlert` with
  "Try again" for a failed read.
- **The composer is compose's.** `features/compose/InlineComposer` is built
  on the same `ComposeMediator` (with `replyToPostId`), `PostBuilder`,
  `ComposeTextBox`, `MentionAutocomplete` and `MediaWidget` as `ComposePage`;
  the request goes through `createPost.ts`, now shared by both.
  "Replying to @username" is visible and is the text box's
  `aria-describedby` (`ComposeTextBox` takes optional `label`, `describedBy`
  and `autoFocus`, defaulting to `/compose`'s behaviour). It takes focus only
  when the modal was opened with `?reply=1`. Submit is "Reply", disabled in
  flight; a failure keeps the draft and shows an `InlineAlert`.
  `features/thread` imports `PostNode` and `feed/api` from feed and
  `InlineComposer` from compose, and nothing else from any feature
  (`thread-isolation.test.ts`).
- **After a reply, the counts come from the server.** The thread's exact key
  and every key under `["feed"]` whose value holds the parent (`cacheHolds`:
  feed pages, search results, other threads) are invalidated. Nothing is
  optimistic, as the human asked.
- **Signed out**: the thread, and in place of the composer a "Sign in to
  reply" link whose `state.from` is `/posts/<id>`.

### Complete-card reveal and the route split (`FRONTEND-015`)

- **One rule, one wrapper.** `features/feed/useCardReady.ts` decides when a
  card is ready; `PreparedPostNode` renders the shared `Skeleton` post
  variant (aria-hidden, `media` reserving the picture frame) until then, and
  the whole `PostNode` in one render after. The feed, search results and the
  thread modal (root and replies) render posts only through it; a profile
  shows no posts yet.
- **Ready** = every picture the card shows (its own; a plain repost's
  original's; `isPlainRepost` moved to `api.ts` for this) has been preloaded
  with `new Image()` and its `decode()` has settled. A rejected decode of a
  picture that did load still counts as loaded. A card with no loadable
  picture is ready on its first render.
- **Bounded**: `CARD_READY_TIMEOUT_MS` (4000), started when the card enters
  the window. A picture still pending then, one that errored, or one with a
  `null` key shows "Image unavailable" in its frame.
- **Windowed**: `usePrepareWindow` observes the skeleton with
  `PREPARE_WINDOW_ROOT_MARGIN` (`0px 0px 100% 0px`, one viewport below) and
  latches. Nothing is requested before that. Without `IntersectionObserver`
  every card counts as in the window.
- **A revealed card stays revealed.** The readiness lives in the card's own
  state, kept per post id plus picture URL. A refetch with the same pictures
  prepares nothing. A changed picture is preloaded again inside the card
  already shown: its frame is empty until it settles, under the same bound.
  Rows keep `key={post.id}`, so a Load more leaves the previous page as it
  is.
- **The frame** (`PostMedia.module.css`): `aspect-ratio: 4 / 3`,
  `object-fit: contain`, letterboxed in `--color-surface-muted`, and the same
  box for the picture, the skeleton's block and the unavailable line. The old
  `max-height: 28rem` and `object-fit: cover` are gone. Inside a prepared
  card the `<img>` is mounted only once loaded (via `CardImageContext`), never
  hidden with CSS. A bare `PostNode` renders it at once.
- **`aria-busy`** sits on the feed's `ol` while the first page's in-window
  cards are being prepared (each reports through `onPreparing`). It latches
  off once they are all ready, so Load more and refetches never set it, and a
  first page without pictures never does. There is no animation anywhere in
  the reveal.
- **Route split.** `routes.tsx` loads the compose, notifications, profile,
  game, player, stats (page and both tabs) and five auth pages with
  `React.lazy` and named-export adapters. `details.tsx` has its own `lazy`
  for the game and player details, which resolves to the same chunks. The
  feed, search, the thread modal, `DetailModal` and the shell stay eager.
  `BackgroundRoutes` wraps the page alone in one
  `<Suspense fallback={<StatusLine>…}>`. `DetailModal` has its own around
  its `<Outlet />`, so a lazy detail never unmounts the dialog. The main
  chunk was 454 kB after the split (it had been 513 kB), so the build no
  longer warns. `lazy-routes.test.ts` pins this through the static import
  graph from `main.tsx`.

  (`["feed", "search", q]`). `TogglePostAction` patches a like or repost optimistically into

  `{ items }` page shape is one `cacheHolds`/`mapCachedPosts` already walk.
  Keyed anywhere else, a like on a search result would not move until the

  `["feed"]` prefix also refetches open search results. `features/search`

## Game page (`FRONTEND-008`)

`src/features/games/`, wired at `/games/:gameId`. **Public**: a game is a read
path ([[0x02-events]]). One read, `GET /events/games/{id}`, through
`features/games/api.ts`, typed by the schema's own `GameDetailOut`,
`TeamBoxScoreOut` and `BoxScorePlayerOut` with no renamed client model.

- **Reached by address only.** Post text (`PostText`) and the Stats page's
  game rows link to `/games/<id>`. One exception to "nothing imports
  `features/games/`": `features/stats` and `features/players` import
  `features/games/format` (the brief: one number format), and nothing else
  from the folder. `features/games` imports no other feature
  (`games-isolation.test.ts` pins both). Moving `format.ts` to a shared

  2OT, `3OT+` (the seventh stored figure is "third overtime and later",
  [[0x02-events]] Game, never split or padded).
- **Dates as stored.** The timestamp is naive US-Eastern; `parseISO` on the
  string without `Z` shows the stored calendar date in every viewer's zone.

  HTML. `\d+` is greedy: `#GameId5012` is 5012, never 501.
- **Box-score names link to `/players/<id>`** (`FRONTEND-009`), inside the
  row's `th scope="row"`; the position stays outside the link, and the
  totals row has none.

  playoffs").

### The stats navigator (`FRONTEND-018`)

Brief 20, stage 2. One navigator for the Stats page and the compose stats
picker (`FRONTEND-021`).

- **Its home is `src/components/stats-nav/`**, outside `features/`, so
  compose may use it. `StatsNavigator` renders a **stack of levels**:
  - a breadcrumb, `nav` "Stats path", whose items return to their level,
    with the last one `aria-current="location"`;
  - Back, shown only when the stack is deeper than one;
  - the top level's `h2` (`tabIndex -1`) and view.
- **The levels are data** (`types.ts`): `{ kind: "season", season, conf }`
  and `{ kind: "team", season, teamId }`. The union is meant to grow (the
  picker adds a game and a box-score level). `SeasonLevel` shows the
  champion and the standings under a `SegmentedTabs` "Conference" bar (All,
  East, West), filtered on the client from the one standings read.
  `TeamLevel` shows the record, the splits and the games. `PlayerResults` is
  the Players search's result list.
- **Router-agnostic, by test.** No file in `stats-nav/` imports
  `react-router-dom` or `features/`, except `features/games/format`.
  - The caller owns the stack, through `open`, `replace` (the conference
    tab) and `pop(toDepth)`.
  - An adapter says how a game or a player is linked. With `levelHref`, the
    level controls are real links whose plain click calls the callback.
  - `StatsNavigator.test.tsx` drives it from React state with no router,
    as the picker will.
- **`SeasonsTab` is the route adapter.**
  - `?season=` and `?conf=east|west` give the season level; All is not
    written, and an unknown value is All.
  - `?team=` gives the team level.
  - `open` and `pop` push the new address, and a conference tab replaces it.
- **Focus** moves to the new level's heading only when a navigator control
  moved the stack. A cold load, the browser's Back or a tab moves none.
- **The reads are `src/api/stats.ts`.** It holds the old `features/stats/api.ts`
  with the same keys, one `ok()` check per fetcher, and `queryOptions`
  factories (`championQuery`, `standingsQuery`, `leadersQuery`,
  `teamSeasonQuery`) with `staleTime` `SEASON_STALE_TIME` (5 minutes).
  - Requests per screen, pinned in `stats-requests.test.tsx`: a cold
    `/stats/seasons` makes 4 (8 before this unit, with the games page; 7
    after it, until `FRONTEND-019` moved the three leader boards); switching
    tabs makes 0; opening a team makes 1; Back makes 0.
- **Lazy.** Nothing in `stats-nav/` or `api/stats.ts` is reachable from the
  entry (`stats-nav-lazy.test.ts`). Since two tabs import it, Rollup puts
  the navigator in a shared `StatsNavigator` chunk (`FRONTEND-019`).
- **No layout shift on load.** The champion's place is two lines tall in
  every state, and the All standings' place is held at the two tables'
  height by a static `Skeleton` while they load.
- **The leaders left Seasons** in `FRONTEND-019`, for Records > Seasonal.

### Records (`FRONTEND-019`)

Brief 20, stage 3, on `EVENTS-010`'s records API ([[0x02-events]] "Records").

- **`/stats/records` is `RecordsTab`**, the route adapter for a `SegmentedTabs`
  "Records view" bar, Historical / Seasonal. The address is the state:

  | Address | Shows |
  |---|---|
  | `/stats/records` | Historical, Team cards |
  | `?group=player` | Historical, Player cards |
  | `?record=<id>` | that record's ranked list |
  | `?view=seasonal[&season=<s>]` | the season's leaders (newest by default) |

  Defaults are never written, and an unknown value is the default. Both bars
  replace the history entry; switching the view drops `group`, `record` and
  `season`. Opening and popping a level push.
- **Two navigator levels**, `{ kind: "records", group }` and
  `{ kind: "record", id }` (`types.ts`), so the breadcrumb, Back and the
  focus rule are the navigator's. Every use of a level narrows by `kind`.
  - `RecordsLevel`: a "Record group" bar (Team / Player), the data window
    ("Since 2003-04, through 2026-27") and the cards. A card's one control is
    "View all" (named "View all: <title>", a real `?record=` link), its
    `::after` stretched over the card so the whole card is the hit area; the
    holder is plain text. While the summary loads, skeleton cards hold the
    place.
  - `RecordLevel`: the rule, "Since <season>" and the whole list (up to 100)
    in one `ScrollTable`, with the API's ranks as given; a column the record
    has no value for is left out. A season record notes that it ranks the
    exact percentage, so equal three-place figures can rank apart. An unknown
    id is "Record not found" in place, with Back.
  - **The record level's group is its list's.** `?record=` never carries
    `group`; until the list or cached summary arrives, the id's prefix
    supplies the group (`FRONTEND-021`, R30). Unknown prefixes retain the
    "Records" fallback. The heading is the record's title from the cached
    summary, else the list.
- **The adapter's optional `teamLink(teamId, season, children)`**: without it
  a team is plain text. `ROUTE_LINKS` gives it through `teamHref`.
- **`SeasonSelect`** (`components/stats-nav/`) is the season picker and its
  loading, error and empty states, shared by Seasons, Seasonal and the picker.
- **The reads are `src/api/records.ts`**: `recordsQuery()` and
  `recordQuery(id)`, both `staleTime: Infinity` (the routes are cached five
  minutes at the edge, R7). A list is one call at `limit=100`; nothing sends
  `offset`; a 404 is `null`. Stats and records share `api/ok.ts` since
  `FRONTEND-021` (R29).
- **Requests per screen**, pinned in `records-requests.test.tsx`: a cold
  `/stats/records` makes 1; Team and Player make 0; opening a card makes 1,
  and Back and reopening it make 0; a cold `?record=` makes 1 and Back from
  it 1; a cold Seasonal makes 4 (seasons and the three boards).
- **Measured** (2026-10-26, `vite preview` against the full load in
  `fanwire_perf`, 360 wide, CPU 4x, five runs): the longest task on a cold
  Records is a median of 108 ms (worst 127); opening the 100-row
  `player-points-game` list 99 ms (142); a cold `?record=` 138 ms (170);
  tabs and Back 0. CLS is 0 on a cold Records and 0.0056 on a cold record.

## Post menu, deletion and account lifecycle (`FRONTEND-012`)

On `POSTS-004` (`DELETE /posts/{id}`, the "Post deleted" placeholders) and
`USERS-003` (`403 account_deactivated`, `POST /users/me/recover`).

- **One account state, `useAccount()`** (`auth/account.ts`), from `useAuth()`
  and the one profile query: `loading`, `anonymous`, `active` (with
  `profile`), `deactivated`, plus `no-profile` (404) and `unavailable` (a
  failed read), which only the guards route on. `fetchProfile` answers
  `ACCOUNT_DEACTIVATED` (a symbol, compared by identity) for that exact 403
  body; any other 403 still throws. The marker is named only in
  `auth/profile.ts` and `auth/account.ts`: the guards, the shell, `PostNode`'s
  controls, `ProfilePage`, `FollowButton`, the thread's reply box and the
  stats pages' "Post about this" links (`offersMemberLinks`) all read the hook.
- **A deactivated account browses as a guest** (the human, 2026-10-22: gated
  on writes, not locked out). Like, repost and follow do what they do for a
  guest (sign-in, no write); the reply box, Report, Delete and "Post about
  this" are absent. Only a *known* deactivation counts: a session whose
  profile is still loading or failed keeps the member's controls. Every page
  shows `routes/Deactivated.tsx`'s `DeactivatedBanner` between the header and
  `main`: a `section` named "Your account is deactivated" (a region, so the
  header stays the one banner landmark), with Recover account and Sign out.
  `RequireAuth` shows `RecoveryScreen` in the route's place (what recovery
  restores, and that individually deleted posts stay deleted), so recovering
  renders the route asked for; `RequireNewProfile` sends it to `/`.
- **Deactivate** is the own-profile settings card's last section, "Account"
  (outside the form): a confirm, then `DELETE /users/me`; on 204 the profile
  entry is read again and every other cache entry is reset. The session stays.
  **Recover** is one `POST /users/me/recover` (disabled in flight); on 200
  every query is invalidated. **Sign out** from the banner also removes the
  cached profile answer.
- **The post menu** (`features/feed/PostMenu.tsx`, on `components/ui/Menu`):
  one "More options" per card, at the end of the action row, rendered only
  while open. Copy link for everyone (`navigator.clipboard.writeText` of
  origin + `/posts/<id>`, then "Link copied" in a status; refused or missing,
  a read-only, focused and selected field with the address). Report for an
  active member on another's post; "Reported", disabled, afterwards, remembered
  per `QueryClient` (`features/feed/reported.ts`, so a reload or a fresh app
  forgets it) and shared by every card of that post. Delete on the active
  member's own post (`post.author.id` against the profile id), never on a
  plain repost. A plain repost's menu acts on the original.
- **`Menu`**: `popover="manual"` shown with `showPopover()` (feature-checked;
  jsdom has none), placed under the button's end edge by script. Arrows,
  Home and End move a roving tab stop; Escape closes it, returns focus to the
  button, and is stopped and default-prevented so a `<dialog>` around it never
  closes; Tab or focus leaving closes it.
- **Confirms are `ConfirmDialog`** (`Dialog` with `role="alertdialog"`, no
  Close button, focus on Cancel, an `InlineAlert` inside on failure, which
  keeps it open). **Nested rule**: a confirm opened in the thread modal is a
  `<dialog>` inside its `<dialog>`; React hands the inner `cancel` and `close`
  to the outer handlers too, so `Dialog` acts only on events whose target is
  its own element. Escape or Cancel closes only the confirm; the modal flow's
  state is untouched.
- **A deletion leaves at once**: `withoutPost` (`features/feed/api.ts`) is
  applied with `setQueriesData` to every entry under `FEED_KEY_ROOT` (feed
  pages, search pages, threads: a thread root becomes `root: null`, a repost's
  original becomes `reposted_post_deleted`), after cancelling in-flight reads;
  then the entries that held it or its parent, and its own thread, are
  invalidated by exact key. 403, 404 and 409 each have their own alert. The
  card's click-to-open ignores clicks inside its own menu and confirms.
- **Focus after a removal** (found in the browser rows: it fell to `<body>`).
  A deleted card hands focus to the next card's "More options", else the
  previous card's, else the list's heading (`tabindex="-1"`); inside the
  thread modal a deleted reply does the same among the replies (the root's
  menu last), and a deleted root hands it to the dialog's Close. It moves only
  if focus was actually lost. After Deactivate, focus goes to the banner
  (`id="deactivated-banner"`, `tabIndex={-1}`), through `mutateAsync`, because
  the own-profile view that ran it has unmounted by then.
- **"Post deleted"** replaces an original whose `reposted_post_deleted` is
  true, on a plain repost and in a quote: a muted box with that text only.
  `reposted_post: null` alone still reads "This post is unavailable".
